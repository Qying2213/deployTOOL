# 管理后台后端发布耗时优化说明

更新时间：2026-09-14

## 问题

原测试服管理后台后端发布流程存在两段重复工作：

1. `deploy --dry-run` 执行完整 Ruff、格式和 pytest，随后 `deploy --yes` 再执行同一套完整门禁；同一提交被连续测试两次。
2. 每次 `deploy --yes` 都隐式执行 `prepare`，重新上传和安装 helper、systemd、Nginx 配置，并提前重启当前服务。普通应用代码发布不需要重复安装这些服务器资源。

随着管理后台测试数量增长，第一项耗时会线性增加；第二项还会产生一次与新版本激活无关的服务重启。

## 调整后的流程

`deploy --dry-run` 现在只执行快速只读预检：

- 校验分支、工作区、Git 操作状态和 upstream；
- 校验 Git diff；
- 校验服务器 helper 版本及完整 SHA256 指纹；
- 执行服务器 preflight；
- 不运行全量业务测试，不打包、上传或切换版本。

`deploy --yes` 现在执行：

1. 校验服务器 helper 版本及 SHA256 指纹；
2. 执行服务器 preflight；
3. 对精确 Git 提交运行一次完整 Ruff、格式和 pytest；
4. 测试后再次校验提交未变化；
5. 构建带清单和逐文件哈希的版本包；
6. 上传、CAS 校验、原子切换、健康检查和失败恢复。

`prepare --yes` 保留为独立管理命令，只用于首次安装，或者 helper、systemd、Nginx 资源经过评审后确实需要升级的情况。普通业务发布不再隐式调用它。

## 安全边界

- 没有提供或放宽 `--skip-tests`；真实发布仍禁止跳过测试。
- `dry-run` 不能代替合并态完整门禁，也不能代替真实发布中的完整门禁。
- helper 不只比较版本号，还比较远端文件与仓库文件的完整 SHA256，避免同版本内容漂移。
- 分支、干净工作区、upstream、发布清单、归档哈希、CAS、全局锁、原子切换、健康检查和自动恢复保持不变。
- 正式服管理后台发布链未改变。

## 验证结果

- 部署工具完整测试：137 项，其中 136 passed、1 项既有 skipped。
- 管理后台发布专项：11 passed。
- Node 与 Bash 语法检查通过。
- 当前测试服真实只读 `dry-run` 通过，helper 版本和 SHA256 指纹匹配。
- 本机实测 `dry-run` 墙钟时间从原流程约 14 秒降至 2.16 秒；测试数量继续增长时，不再产生第二次完整 pytest 的额外耗时。
- 本轮没有重新发布管理后台业务代码，没有修改服务器配置、数据库或 `.env`。
